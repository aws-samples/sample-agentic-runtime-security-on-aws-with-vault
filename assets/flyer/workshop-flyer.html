Agentic Runtime Security on AWS

AI agents broke the assumptions security tooling has relied on for two decades. An agent is not a user, and not a workload in the classic sense — it acts on its own behalf one request and on a person's behalf the next. In this workshop you deploy a working implementation of five control objectives for agentic systems on EKS, using IBM Verify Identity Access and HashiCorp Vault Enterprise 2.0.3 and its native AI agent support: every agent has a verifiable identity, no standing privileges, actions are tied to user intent, enforcement happens at the point of use, and audit evidence correlates across all three trust planes.

Vault's native AI agent support — released, and configured by you here

Agent Registry Each agent is a first-class identity, distinct from human users and from traditional non-human identities.
Agent ceiling policies The maximum an agent may ever hold. A ceiling restricts and never grants — effective permission is the human's baseline ∩ the agent's ceiling.
OAuth resource server The issued OAuth token authorizes Vault directly. No login round-trip, no intermediate Vault token, no auth method in that path at all.
Per-request RAR Authorization details of type: vault:path_access narrow a token to the exact path and capability of a single request. Vault is the decision point.

The agentic threat model spans three planes at once

User identityWho is asking?

Data planeWhat credential does it present?

What you build — three agents, each layering on the last

  1. Non-personalized read-only agent Workload identity and just-in-time database credentials. No standing grants.
  2. OAuth personalized read-only agent User intent carried into the request via Authorization Code + PKCE.
  3. Privileged action with CIBA Out-of-band approval for a real money movement, then one query correlating identity, workload and database evidence for that single action.
